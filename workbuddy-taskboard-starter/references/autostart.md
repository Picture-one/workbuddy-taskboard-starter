# 开机自启与「自启到底有没有生效」的判定

## 载体：注册表 Run 键（不是启动文件夹，也不是计划任务）

```
HKCU\Software\Microsoft\Windows\CurrentVersion\Run
    值名 Taskboard
    值   "<绝对路径 pythonw.exe>" "<绝对路径 autostart-taskboard.pyw>"
```

| 候选方案 | 结论 |
|---|---|
| `schtasks /SC ONLOGON` 计划任务 | ❌ 本机实测被 ACL 拒绝：`C:\Windows\System32\Tasks` 根目录只给 Administrators / SYSTEM 写权限，**连一个 `notepad.exe` 的探针任务都 `Access is denied`**。要提权就得点 UAC |
| 启动文件夹放 `start-taskboard.cmd` | ❌ 会闪一个黑窗口，而且关掉窗口服务就停 |
| 启动文件夹放 `.vbs` + `wscript` | ❌ 工具安全策略把 wscript/cscript 判为 LOLBin，直接拦 |
| COM 建 `.lnk`（`WScript.Shell`） | ❌ 安全策略禁 COM 实例化 |
| 启动文件夹放 `.pyw` 指针文件 | ❌ **见下面那条坑 —— 会静默失败** |
| **`HKCU\...\Run` 值 + 绝对路径 `pythonw.exe`** | ✅ **免提权、不弹窗、已实测通过** |

---

## ⚠️ 第一大死因：`.pyw` 会走到「僵尸解释器注册」上

**现象**：开机/登录后服务没起来，而 `logs\autostart.log` 里**一条记录都没有** ——
连"文件被打开追加"都没发生。查事件日志也**没有任何痕迹**。

**根因链条**：

```
自启项写的是 .pyw 文件路径
  → .pyw 的文件关联指向 pyw.exe（Python Launcher，GUI 子系统）
  → 指针文件没有 shebang，于是 Launcher 用「默认解释器」
  → 默认版本由注册表 PEP 514 里版本号最高的那条决定
  → 若存在「僵尸注册」（例如 3.14 → C:\Python314，而该目录根本不存在）
  → CreateProcess 失败，退出码 101
```

**为什么这么难查**：`pyw.exe` 是 GUI 子系统进程，不写控制台、不写事件日志，
失败得**完全静默**。

**怎么只读地提前发现**：

```bash
py.exe -0        # 看默认版本（* 号打在哪一行）
py.exe -0p       # 列出所有可见解释器及其路径
```

把 `*` 那一行的路径拿去检查**文件是否存在**。不存在 = 这条链路随时会静默失败。

**对策**：自启值**直连绝对路径 `pythonw.exe`**，彻底绕开 `.pyw` 关联。自检里有一条哨兵
专门做这个检查。

---

## 启动器做了什么（`autostart-taskboard.pyw`）

1. **先写 banner**，再干别的 —— 保证「有没有执行」永远有痕迹
2. 解析 `start-taskboard.cmd` 取环境变量（**保持配置单一真源**，不在启动器里再写一份端口/origin）
3. 延迟一小会儿再起服务（等桌面会话稳定）
4. 以 `CREATE_NO_WINDOW` 拉起 Node（无黑窗）
5. 轮询 `/health`，等到服务真的可用
6. 写状态文件 `logs\last-logon.json`（机器可读：`result`/`port`/`node_pid`/`boot` 等）
7. **顶层 `try/except` 兜底**，异常时记 traceback 并以退出码 70 结束 —— 绝不静默

## 「自启到底生效了没有」怎么判

**不要看「日志里有没有内容」** —— 这个文件同时是 Node 子进程的 stdout/stderr 落地点，
里面有大量无时间戳输出；而且它可能被清空过。

**正确判据：带时间戳的 banner + 本次登录时间**

| 要素 | 怎么拿 |
|---|---|
| 最近一条 banner 的时间戳 | `logs\autostart.log` 里最后一条 `=== logon run ===` 记录 |
| **本次登录时间** | `explorer.exe` / `sihost.exe` 的**最早创建时间**（容差 120 秒）。用 `ctypes` + `GetProcessTimes` 读，纯标准库 |

判定：**banner 时间戳晚于本次登录时间** → 自启生效。

⚠️ 两个必须避开的陷阱：

1. **别用 `winlogon.exe` 判登录时间** —— 它是**开机**就启动的（属会话 1），混进来会让
   「登录时间」退化成「开机时间」，**「注销后重登」这个场景直接失效**。
2. **别只信 uptime**。快速启动（hiberboot）保留内核会话，`GetTickCount64` /
   `LastBootUpTime` **不重置** —— 会出现"电脑明明刚启动过，却显示已运行几十小时"的假象。
   要看 `Kernel-Boot` 事件（18 / 27 / 32）或进程创建时间。

### banner 里为什么要记 `argv`

`argv` 是判断"这条记录到底谁触发的"的关键：

* 触发器（Run 值 / 计划任务 Action / 启动文件夹指针）**都不带参数** → `argv=[]`
* 手工调试往往带 `--port` 之类的参数 → `argv` 非空

但要注意：**agent 或你自己手工跑启动器时同样不带参数**，所以 `argv=[]` 本身**不能**证明
是登录触发的。硬判据仍是**时间戳晚于本次登录时间**，并且要保证顺序正确：
**先确认已完成重新登录，再看此后的 banner。**

## 自检（`selfcheck-taskboard.cmd`）

双击即可。它是**严格只读**的（只读文件 + 打印到屏幕），十多项检查，覆盖：

* 上游代码 / 解释器 / Node 是否存在
* 自启注册表值（解释器路径必须存在）
* 自启项有没有被系统禁用（`StartupApproved`）
* 启动文件夹是否残留旧指针（会与 Run 键各写一条记录、还抢同一个端口）
* origin 白名单两处是否逐字符一致
* banner 与解析格式是否同步
* 哨兵：`py.exe -0` 的默认解释器是否存在（就是上面那条坑）

退出码：

| 码 | 含义 |
|---|---|
| `0` | 通过 |
| `1` | 执行过，但服务不健康 |
| `2` | 本次登录**未执行**自启 |
| `3` | 无法判定（时间戳对不上，会说明原因） |
| `10` | 配置或文件有问题 |

> **不要反复重置 `autostart.log`。** 重置会把「本次登录是否执行过」的判据一起毁掉 ——
> 日志 mtime 晚于登录时间却没有任何 banner，自检只能判「无法判定」。

## 真正的验证：注销 → 重新登录

手工跑一次启动器只能证明**动作通路**（解释器在、命令行对、服务能起来）。
**只有一次真实登录，才能证明触发点本身有效** —— 没有任何模拟手段可以替代。

**用「注销」而不是「切换用户」**：切换用户是新建会话、旧会话还挂着，验证不干净。

步骤：

1. 存档手头工作（注销会关掉所有程序）
2. `Win + R` → `shutdown /l` → 回车（最快的注销方式）
3. 重新登录，**等 60~90 秒**（启动器有延迟 + 起服务要几秒）
4. 双击 `selfcheck-taskboard.cmd`，看【结论】行

期望：`✅ 自启生效，服务健康` + 退出码 `0`。
